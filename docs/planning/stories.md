### 1.3 Decision spike: `feature_type` — TEXT + CHECK vs. Postgres ENUM

**Resolved 2026-08-17: Postgres `ENUM`** (`feature_type_enum AS ENUM ('road', 'path', 'route')`), overriding this doc's original TEXT+CHECK leaning. Reasoning, per Sean's own test ("is this business logic/projecting OSM onto our model, or informational passthrough?"): `feature_type` has no OSM-native equivalent — it's the output of `transform_way_feature`'s classification logic (application-layer.md §5) dispatching on `highway`/`route` tag values — and it drives real downstream branching in both the API's per-type property mapping and the frontend's per-layer filters. That's the business-logic case, not the passthrough case, so a typed enum wins: `Npgsql.EntityFrameworkCore.PostgreSQL` maps it directly to a C# `FeatureType` enum (compile-time-checked, autocomplete-friendly), and EF Core's migration tooling (per 1.2's EF Core decision) generates the `ALTER TYPE ... ADD VALUE` DDL automatically when a new C# member is added — neutralizing most of the classic "enum evolution is awkward" downside. Recorded in persistence-layer.md §1.1/§9 and epics.md §4 row 2.

**Acceptance criteria (all satisfied by the resolution above):**

- ~~Sean has explicitly signed off.~~ Done — ENUM.
- ~~Decision recorded.~~ Done, across persistence-layer.md §1.1/§9 and epics.md §4.

**Blocks:** 1.6 (schema DDL needs this settled before the `feature_type` column definition is written) — now unblocked on this point; 1.6 should define `feature_type_enum` (or the equivalent EF Core `HasPostgresEnum<FeatureType>()` model configuration) before the `features` table itself.

### 1.6 Initial schema migration: `features` table, constraints, indexes

Author the first real EF Core migration (via `dotnet ef migrations add InitialCreate` against the `BikeMapDbContext`/entity model from 1.5, per 1.2's resolution) containing exactly the schema from [persistence-layer.md §1.1](./layers/persistence-layer.md#11-one-table-one-row-per-osm-element): `CREATE EXTENSION IF NOT EXISTS postgis;`, a `feature_type_enum AS ENUM ('road', 'path', 'route')` type (per 1.3's resolution — modeled in C# as a `FeatureType` enum via `Npgsql.EntityFrameworkCore.PostgreSQL`'s `HasPostgresEnum<FeatureType>()`), and the `features` table with `id BIGSERIAL PRIMARY KEY` (per 1.4's resolution — surrogate, first-class), `osm_type TEXT NOT NULL CHECK (osm_type IN ('way', 'relation'))`, `osm_id BIGINT NOT NULL`, `feature_type feature_type_enum NOT NULL`, `geom geometry(Geometry, 4326) NOT NULL`, the road columns (`cycleway_left`, `cycleway_right`, `cycleway_left_buffer`/`cycleway_right_buffer` `BOOLEAN NOT NULL DEFAULT FALSE`), the path column (`bicycle`), the route columns (`route`, `cycle_network`, `ref`, `name`, `state`), `tags JSONB NOT NULL DEFAULT '{}'::jsonb`, and `first_seen_at`/`last_seen_at TIMESTAMPTZ NOT NULL DEFAULT now()`. Include `CONSTRAINT ux_features_osm_key UNIQUE (osm_type, osm_id)` (enforcing Contract B's key without it being the PK), `CONSTRAINT chk_features_geom_valid CHECK (ST_IsValid(geom))`, `CONSTRAINT chk_features_geom_type CHECK (GeometryType(geom) IN ('LINESTRING', 'MULTILINESTRING'))`, `CREATE INDEX idx_features_geom ON features USING GIST (geom)`, and `CREATE INDEX idx_features_feature_type ON features (feature_type)`. No GIN index on `tags` — explicitly deferred per §1.2 until a query pattern needs it.

**Acceptance criteria:**
- Applying the migration via `dotnet ef database update` against a fresh `db` creates `feature_type_enum` and `features` with exactly the columns, types, and defaults listed above (verify via `\d+ features` and `\dT+ feature_type_enum`).
- `INSERT`ing a row with a self-intersecting `LineString` (invalid geometry) fails on `chk_features_geom_valid`, not on a downstream error.
- `INSERT`ing a `Point` geometry fails on `chk_features_geom_type`.
- `INSERT`ing a second row with the same `(osm_type, osm_id)` pair (no `ON CONFLICT` clause) fails on `ux_features_osm_key`.
- `INSERT`ing a `feature_type` value outside `'road'`/`'path'`/`'route'` is rejected by the enum type itself (not a CHECK constraint).
- `idx_features_geom` exists and is reported as a GiST index (`pg_indexes` / `\di`); `idx_features_feature_type` exists as a B-tree.
- Re-running the full migrate-from-empty sequence (1.5 + this migration) is repeatable — tearing down the `pgdata` volume and reapplying reproduces an identical schema.

**Blocked by:** 1.5. (1.3 and 1.4 are now resolved — ENUM and surrogate PK respectively — so this story implements those decisions directly rather than waiting on them.)
**Blocks:** 1.7, 1.8, 1.9.

### 1.7 One-off validation loader: `data/export.geojson` → `features`

Write a throwaway script (e.g. `scripts/load_export_to_postgis.py`, explicitly not the real ingestion loader — that's Epic 4's job, and this file gets deleted once Epic 4 lands) that reads today's `data/export.geojson`, connects to the `db` service from 1.1, and executes the `INSERT ... ON CONFLICT (osm_type, osm_id) DO UPDATE` from [persistence-layer.md §5](./layers/persistence-layer.md#5-idempotent-upsert-support) per feature, using `ST_GeomFromGeoJSON(%(geometry_json)s)` for `geom` and leaving `first_seen_at` untouched on conflict while bumping `last_seen_at = now()`. Add `psycopg` (v3, matching the real loader's eventual choice per application-layer.md §6, so nothing has to change later) to `scripts/requirements.txt`.

One real gotcha to build around, not gloss over: `data/export.geojson`'s route-relation features currently have `properties.type` clobbered to `"route"` by the exact bug epics.md's Epic 4 §"Must-fix, blocking" #1 describes (`transform_relation_feature` spreads OSM's own `type: "route"` tag over the original `"relation"` value) — verified directly against the current file: way-derived features keep `properties.type == "way"`, but every route-relation feature has `properties.type == "route"`, never `"relation"`. Since this loader only targets today's already-broken file and Epic 4's fix is out of scope here, derive `osm_type` as `"way"` when `properties.type == "way"` and `"relation"` otherwise (every non-`"way"` feature in the current export is a route relation) — document this inline as a known workaround tied to the Epic-4 bug, not a general rule.

**Acceptance criteria:**
- Running the script against a freshly-migrated, empty `db` inserts one row per feature in `data/export.geojson`; row count matches `len(features)` in the file.
- `osm_type` is populated correctly for both ways and relations despite the `properties.type` clobbering bug (spot-check: a known route relation, e.g. "Little Sugar Creek Greenway," lands with `osm_type = 'relation'`).
- Running the script twice against the same `db` leaves the row count unchanged, `first_seen_at` unchanged, and `last_seen_at` advanced on every row (idempotent UPSERT).
- The script is documented (README comment or `CLAUDE.md` one-liner) as a throwaway validation tool, explicitly not wired into `osm-refresh.yml`.

**Blocked by:** 1.1 (running `db`), 1.6 (schema to load into).
**Blocks:** 1.8 (integration tests can use this as a convenient fixture-loading path, though 1.8 can also load fixtures directly).

### 1.8 Integration tests: idempotent UPSERT, bbox query, constraint rejection

Per [persistence-layer.md §8](./layers/persistence-layer.md#8-testing-approach-persistence-layer), add integration tests that run against the containerized `db` service (same container locally and in CI, per testing-and-tooling.md §1's "one definition, two uses" — CI wiring itself is Epic 7's job, this story only needs the tests to exist and pass locally against `docker compose up db`). Apply migrations from empty, load a small fixture set of features (a handful of hand-written rows spanning `road`/`path`/`route`, not the full `export.geojson`), and assert against them.

**Acceptance criteria:**
- Idempotent UPSERT: loading the same fixture batch twice leaves row count and every row's `first_seen_at` unchanged, while `last_seen_at` advances on the second load.
- Bbox query correctness: a query using the `&&` + `ST_Intersects(geom, ST_MakeEnvelope(...))` pattern from persistence-layer.md §2 returns fixture features whose geometry falls inside a given envelope and excludes ones outside it.
- Constraint rejection: an insert with an invalid geometry is rejected (fails on `chk_features_geom_valid`); an insert reusing an existing `(osm_type, osm_id)` without `ON CONFLICT` is rejected (fails on the unique/PK constraint) — neither silently succeeds or silently corrupts data.
- Tests are runnable with a single documented command (e.g. `pytest scripts/tests/test_persistence_integration.py` or equivalent) against `docker compose up db`, and that command is in `CLAUDE.md`.

**Blocked by:** 1.6 (schema must exist). Can reuse 1.7's UPSERT SQL as a reference but doesn't require running the loader script itself.

### 1.9 (Optional) Index-usage regression test via `EXPLAIN (ANALYZE)`

Per persistence-layer.md §8's "optionally" — cheap insurance, not required for the epic to be done. Add a test that loads a realistically-sized fixture set (hundreds to low-thousands of rows, not just the handful from 1.8) and runs `EXPLAIN (ANALYZE)` on a representative bbox query, asserting the plan includes a `Bitmap Index Scan` on `idx_features_geom` rather than a sequential scan. This guards against a future migration accidentally dropping or invalidating the spatial index without anyone noticing until production latency degrades.

**Acceptance criteria:**
- Test loads a fixture set large enough that Postgres's planner would prefer an index scan over a sequential scan for the test bbox (verify this is actually true for the chosen fixture size — too small and the planner legitimately picks a seq scan, giving a false failure).
- `EXPLAIN (ANALYZE)` output for the bbox query is parsed or pattern-matched for `Bitmap Index Scan` / `idx_features_geom`.
- Test is clearly marked optional/slow (e.g. a separate pytest marker) so it doesn't block the fast feedback loop of 1.8's tests.

**Blocked by:** 1.6, and pairs naturally with 1.8 but can land independently since it's optional.

### 2.8 `FeaturesRepository`: Dapper query against `features` (Contract C)

Implement `api/Features/FeaturesRepository.cs` per [api-layer.md §3](./layers/api-layer.md#3-query-implementation): a hand-written parameterized SQL query via Dapper (not EF Core — api-layer.md §3 is explicit this is a deliberate choice, independent of whatever migration tooling Epic 1 picks) against the `features` table:

```sql
SELECT osm_type, osm_id, feature_type, geom,
       cycleway_left, cycleway_right, cycleway_left_buffer, cycleway_right_buffer,
       bicycle, route, cycle_network, ref, name, state
FROM features
WHERE geom && ST_MakeEnvelope(@minLon, @minLat, @maxLon, @maxLat, 4326)
  AND ST_Intersects(geom, ST_MakeEnvelope(@minLon, @minLat, @maxLon, @maxLat, 4326));
```

incorporating 2.2's clipping decision for the `feature_type = 'route'` case (either an `ST_Intersection(...)` wrapped `geom` column or a documented no-op, per whichever the spike concluded). `geom` deserializes to an NTS `Geometry` via the `Npgsql.NetTopologySuite` plugin registered against the Npgsql data source — no manual WKB/WKT parsing. The repository returns a small internal row DTO (not yet the GeoJSON `Feature` shape — that mapping is `FeaturesService`'s job in 2.9), keeping this class's only responsibility "run the query, get typed rows back."

**Acceptance criteria:**
- Query issues both `&&` and `ST_Intersects` explicitly (not relying on `ST_Intersects` alone), matching the documented reasoning that `&&` is what hits the GiST index.
- `geom` column round-trips to an NTS `Geometry`/`MultiLineString` with no manual parsing code.
- The route-relation branch reflects 2.2's decision (clipped or whole) with a code comment linking to the spike's recorded finding.
- Repository method signature accepts a validated bbox (post-`BboxParser`), not raw query-string floats — it does not re-validate.
- Integration-level test (can live here or wait for 2.14) confirms a feature whose geometry bbox overlaps the query envelope but whose actual geometry doesn't intersect (a non-axis-aligned way) is correctly excluded by `ST_Intersects`.

**Blocks:** 2.9 (FeaturesService).

### 4.10 Acquire step: download, cache, integrity-check, and cached-`.pbf` fallback

`application-layer.md` §3.1 + §7. Download the Geofabrik North Carolina `.osm.pbf` (`https://download.geofabrik.de/north-america/us/north-carolina-latest.osm.pbf`, ~300 MB) plus its companion `.osm.pbf.md5` over HTTPS into a stable gitignored cache (`data/osm-cache/north-carolina-latest.osm.pbf`), keyed by the day; in CI, back it with `actions/cache` keyed on the date so a same-day re-run (PR push, manual dispatch) reuses it. Full nightly re-download is the v1 model (per 4.2). Verify the download against the `.md5` and a size floor (a ~2 KB body is a CDN error page, not an extract). Resilience (§7, replacing the retired Overpass backoff loop): a few retries with a modest fixed / linear delay for **transient** CDN/network errors only — no 429 / `Retry-After` semantics, Geofabrik serves a static file; on exhausted retries **or** a checksum mismatch, **proceed with the last successfully cached `.pbf`** and log loudly that data may be ≥24 h stale; hard-fail only when there is no cached copy at all (first-ever run). `osmium` / `osm2pgsql` steps get **no** retry logic — a failure there is a real bug and should fail visibly. Acquire and its fallback are one cohesive PR: splitting the fallback out would leave a first story that can't safely run in CI and a second that is only error paths. Files touched: `scripts/pipeline/acquire.py`, `scripts/requirements.txt` (an HTTP lib if not already present), `.gitignore`, `scripts/tests/`.

**Acceptance criteria:**
- A successful run downloads the `.pbf` + `.md5`, verifies the MD5 matches and the file exceeds the size floor, and places it at the cache path.
- A same-day re-run with a warm cache performs no re-download (and in CI, `actions/cache` restores it) — verified by test/inspection that no HTTP GET for the `.pbf` is issued.
- An injected transient HTTP error (e.g. a 503 then success) is retried and the run proceeds; a persistent transient error exhausts the retries.
- On exhausted retries *or* an MD5 mismatch, with a previous `.pbf` in the cache: the step returns that cached file, exits without error, and emits a clear "proceeding on stale extract" log line including the cached file's age.
- On the same failure with an empty cache: the step hard-fails with an actionable error.
- A truncated / tampered download (below the size floor, or MD5 mismatch) is never promoted to the cache path as the new "last good" copy.

### 4.14 Ingestion SQL: six-clause reproduction, `DISTINCT ON`, EWKB out

`application-layer.md` §3.4 + §6.2. A single query against `osm_raw` reproducing exactly what the old Overpass QL selected — the six positive clauses (`way[~"^cycleway:.*$"~"."]`, `way["cycleway"~"."]`, `way["highway"="cycleway"]`, `way["bicycle"="designated"]`, `way["bicycle"="yes"]`, `relation["route"="bicycle"]`) `UNION`ed, minus `way["highway"="proposed"]` (`AND coalesce(tags->>'highway','') <> 'proposed'`) — emitting `osm_type`, `osm_id`, full `tags`, and `ST_AsEWKB(geom) AS geom_ewkb`. `UNION` (not `UNION ALL`) + `DISTINCT ON (osm_type, osm_id)` collapse a way matching more than one clause (and, as a cheap second layer over 4.12's merge-first, any clip-overlap dupe) to one row. Geometry leaves as **EWKB** (per 4.2) — the pure transforms never touch geometry, so there is no reason to serialize it to GeoJSON and re-parse it. The coarse tag selection is the flex config's job; this SQL does the *exact* six-clause reproduction, kept in SQL adjacent to Python and unit-testable — not in Lua. **Acceptance criteria:**

- The multi-clause way appears exactly once.
- A `cycleway:`-prefixed key matches only when its value is non-empty (mirrors Overpass `~"."`).
- `geom_ewkb` round-trips: `ST_GeomFromEWKB(geom_ewkb)` reproduces the source geometry with SRID 4326 preserved.

### 4.15 Adapter: raw row → transform-input dict

### 6.2 Bbox area cap (`Features:MaxBboxAreaDegrees`)

**Lands inside:** Epic 2

### 6.4 Structured request logging (bbox, area, feature count, duration, payload size)

### 6.5 `scripts/check_data_quality.py`

**Lands inside:** Epic 4

Write `scripts/check_data_quality.py`, a standalone script run against PostGIS after ingestion, per application-layer.md §9's "Data-quality checks" subsection. It performs three checks, distinct from the pytest code-correctness suite because they validate *this run's data*, not the code: (1) feature-count sanity per configured area — query PostGIS for a rough feature count within each area's bbox and compare against a floor (not zero, or not less than some percentage of the prior run's count) to catch a broken clip or bad AOI polygon yielding empty/truncated results for one area; (2) geometry validity — `ST_IsValid(geom)` over newly-touched rows, catching malformed geometries from the `osm2pgsql`/`osmium` geometry assembly before they reach the API layer; (3) duplicate OSM id tripwire — a `GROUP BY (osm_type, osm_id) HAVING COUNT(*) > 1` query that should always return zero rows given the UPSERT's unique constraint, cheap enough to run every time as a smoke test that the constraint itself hasn't broken. The script exits non-zero if any check fails and is independently runnable locally, not folded into the loader.

**Acceptance criteria:**
- `python scripts/check_data_quality.py` connects to PostGIS using the same env-var-driven connection config as the loader (`DATABASE_URL`/`PG*`), consistent with testing-and-tooling.md §1's local/CI parity.
- Feature-count check: fails (non-zero exit, printed reason) when a configured city's post-load feature count is zero or falls below the configured floor relative to the prior run.
- Geometry validity check: fails when any row's `geom` fails `ST_IsValid`, and reports the offending `(osm_type, osm_id)` pairs.
- Duplicate check: fails when the `(osm_type, osm_id)` `GROUP BY ... HAVING COUNT(*) > 1` query returns any rows, and reports them.
- All three checks pass (exit 0) against a known-good loaded dataset.
- The script is runnable standalone/locally against the docker-compose PostGIS instance, independent of GitHub Actions.

**Blocks/blocked by:** Blocked by Epic 4's loader existing (needs real UPSERTed data in PostGIS to check) and by Epic 1's schema (needs the `features` table and its `(osm_type, osm_id)` unique constraint to exist). Blocks 6.6.
